# Авторизация и «прогретые» аккаунты

Документ объясняет, как автоматизация получает доступ к публичной выдаче Авито,
почему «обычный» браузер работает, а «чистый» автоматизированный — нет, и как
подготовить профиль (в том числе для аккаунта продавца в фазе массового редактирования).

## Почему это вообще нужно

- Авито защищается фаерволом (hCaptcha + поведенческие проверки) и **не отдаёт
  результаты поиска в headless-режиме** — приходит пустая оболочка без объявлений.
- Доверие даётся связке «cookies + отпечаток браузера + история». У обычного браузера
  оно есть, у свежей автоматизированной сессии — нет.
- Страница «Доступ ограничен: проблема с IP» — это заглушка фаервола, а не блокировка
  IP: тот же IP из обычного браузера работает.

Отсюда правило: автоматизация работает в **постоянном профиле** полного Chromium,
в видимом режиме (или под Xvfb на сервере), с cookies, полученными один раз вручную.

## Где хранится профиль

- Каталог задаётся `BROWSER_USER_DATA_DIR` (по умолчанию `.browser-profile` в каталоге
  `backend/`, в Docker — `/data/browser-profile` в томе `browserdata`).
- Профиль содержит cookies доступа — **не коммитится и не передаётся третьим лицам**
  (`.browser-profile/` в `.gitignore`).
- Права на каталог: `chmod 700 backend/.browser-profile`.

## Способ 1. Браузерный логин (`browser-login`)

Подходит, когда есть рабочий стол (ноутбук) или Xvfb.

```bash
cd backend
make browser-login
# или: .venv/bin/python scripts/browser_login.py --url "https://www.avito.ru/"
```

1. Откроется окно полного Chromium с постоянным профилем.
2. Пройдите проверку Авито (капча/галочка), если она появилась.
3. Скрипт сам определит, что проверка пройдена, сделает прогрев и сохранит профиль.
4. Пропишите в `.env`: `BROWSER_USER_DATA_DIR=.browser-profile` и
   `BROWSER_HEADLESS=false`.

Для аккаунта продавца: в этом же окне войдите в кабинет — сессия сохранится в профиле.
Все дальнейшие ручные действия (правки, публикации) в фазе 6 будут выполняться в этом
профиле.

## Способ 2. Импорт cookies из обычного браузера

Подходит, когда в браузере (Brave/Chrome/Firefox) Авито уже работает, а окно
автоматизации неудобно или сервер без графики.

1. Установите расширение **Cookie-Editor** (или откройте DevTools → Network → любой
   запрос к avito.ru → Request Headers → `cookie`).
2. На avito.ru: Export → JSON (сохранить файл).
3. Импорт:

```bash
cd backend
.venv/bin/python scripts/import_cookies.py --file ~/Downloads/cookies.json
# или строкой из DevTools:
.venv/bin/python scripts/import_cookies.py --cookie "v=...; u=...; ft=..."
```

Скрипт добавит cookies в профиль, откроет страницу поиска и проверит доступ:
`OK: доступ есть` или `FAIL: cookies не дали доступ` (обновите cookies).

## Проверка, что всё работает

```bash
cd backend
.venv/bin/python scripts/fetch_page.py --browser \
  --url "https://www.avito.ru/moskva/telefony?q=iphone+15" --out /tmp/page.html
```

Ожидаемо: `page 1: 50 listings` и карточки с ценами. Если ноль — обновите профиль
(способ 1 или 2).

## Сервер (без рабочего стола)

- В Docker браузерный воркер уже запускается под **Xvfb** (`xvfb-run`, `BROWSER_HEADLESS=false`),
  профиль живёт в томе `browserdata`.
- Локально воркер запускается из Chrome-кэша хоста: `make up-dev` (без скачивания
  Chromium в образ). На сервере соберите self-contained образ: `INSTALL_BROWSER=1 docker compose build worker`.
- Первичное доверие на сервере получают так: импортируют cookies (`import_cookies.py`
  можно запускать в контейнере — окно уходит на Xvfb и не мешает) **или** копируют
  готовый профиль с ноутбука в том:

```bash
docker compose cp backend/.browser-profile/. worker:/data/browser-profile
```
- Для объёмов и стабильности используйте **резидентные прокси**:
  `PROXY_ENABLED=true`, `PROXY_URL=http://user:pass@host:port`. Прокси подключается и в
  браузерном транспорте, и в HTTP.
- Один прокси ↔ один профиль: не смешивайте выходные IP у одного профиля.

## Диагностика

| Симптом | Причина | Действие |
|---|---|---|
| Пустая страница, 0 карточек, title «Авито» | headless-детект | `BROWSER_HEADLESS=false` (+ Xvfb на сервере) |
| «Доступ ограничен: проблема с IP» / 439 / hCaptcha | фаервол не доверяет сессии | `make browser-login` или `import_cookies.py` |
| 429 после ~10 страниц | троттлинг | обход сам остановится; увеличить паузы (`CRAWL_DELAY_*`), снизить `CRAWL_MAX_PAGES_PER_RUN`, использовать прокси |
| Внезапно снова капча | истёк/недостаточен профиль, сменился IP | повторить прогрев; закрепить прокси за профилем |

## Безопасность и правила

- Cookies и профиль — это доступ к аккаунту: храните локально, не публикуйте.
- Для автоматизации лучше отдельный аккаунт, отдельный профиль и отдельный прокси.
- Соблюдайте умеренную частоту: паузы 8–20 секунд, до 10 страниц за обход,
  расписание 1–2 часа и реже на старте. Парсинг публичных страниц — на ваш риск и
  в рамках действующих правил площадки.
- Телефоны и персональные данные проект не собирает.
