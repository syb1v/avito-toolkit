# Авторизация и «прогретые» аккаунты

Документ объясняет, как автоматизация получает доступ к публичной выдаче Авито,
почему «обычный» браузер работает, а «чистый» автоматизированный — нет, и как
подготовить профиль (в том числе для аккаунта продавца в фазе массового редактирования).

## Почему это вообще нужно

- Авито защищается фаерволом (hCaptcha + поведенческие проверки) и **не отдаёт
  результаты поиска в headless-режиме** — приходит пустая оболочка без объявлений.
- Доверие даётся связке «cookies + отпечаток браузера + история». У обычного браузера
  оно есть, у свежей автоматизированной сессии — нет.
- Страница «Доступ ограничен: проблема с IP» — это заглушка фаервола, а не блокировка
  IP: тот же IP из обычного браузера работает.

Отсюда правило: автоматизация работает в **постоянном профиле** полного Chromium,
в видимом режиме (или под Xvfb на сервере), с cookies, полученными один раз вручную.

## Где хранится профиль

- Каталог задаётся `BROWSER_USER_DATA_DIR` (по умолчанию `.browser-profile` в каталоге
  `backend/`). В dev-стеке (`make up-dev`) воркер монтирует `./backend:/srv` и читает
  `/srv/.browser-profile` — **тот же профиль**, что и скрипты `make cookies` /
  `make browser-login`. В prod-образе профиль лежит в томе `browserdata`
  (`/data/browser-profile`); перенести туда профиль можно через
  `docker compose cp backend/.browser-profile/. worker:/data/browser-profile`.
- Профиль содержит cookies доступа — **не коммитится и не передаётся третьим лицам**
  (`.browser-profile*/` в `.gitignore`).
- Права на каталог: `chmod 700 backend/.browser-profile`.

## Способ 1. Автоимпорт cookies из браузера (`make cookies`)

Самый надёжный путь: ваш обычный браузер уже прошёл проверки Авито, забираем его
cookies напрямую и кладём в чистый профиль автоматизации.

```bash
make cookies                 # по умолчанию Brave
make cookies BROWSER=chrome  # chrome | chromium | edge | firefox | librewolf | opera | vivaldi
# вручную: cd backend && .venv/bin/python scripts/import_cookies.py --from-browser brave --fresh
```

- Браузер читается через `browser-cookie3` (Linux: ключ из gnome-keyring/kwallet);
  значения cookies никуда не печатаются.
- Флаг `--fresh` сбрасывает старый профиль — это лечит «сожжённые» cookies после
  сотен страниц.
- Скрипт сразу проверяет выдачу: `Проверка: челлендж=нет, объявлений=50` и `OK`.
- Повторяйте `make cookies`, если Авито снова начал показывать челлендж: сессия в
  вашем браузере всегда довереннее автоматизированной.

## Способ 2. Браузерный логин (`browser-login`)

Подходит, когда есть рабочий стол (ноутбук) или Xvfb.

```bash
cd backend
make browser-login
# или: .venv/bin/python scripts/browser_login.py --url "https://www.avito.ru/"
```

1. Откроется окно полного Chromium с постоянным профилем.
2. Пройдите проверку Авито (капча/галочка), если она появилась.
3. Скрипт сам определит, что проверка пройдена, сделает прогрев и сохранит профиль.
4. Пропишите в `.env`: `BROWSER_USER_DATA_DIR=.browser-profile` и
   `BROWSER_HEADLESS=false`.

Для аккаунта продавца: в этом же окне войдите в кабинет — сессия сохранится в профиле.
Все дальнейшие ручные действия (правки, публикации) в фазе 6 будут выполняться в этом
профиле.

## Способ 3. Ручной экспорт cookies

Подходит, когда автоматический импорт недоступен (нестандартный браузер/сервер).

1. Установите расширение **Cookie-Editor** (или откройте DevTools → Network → любой
   запрос к avito.ru → Request Headers → `cookie`).
2. На avito.ru: Export → JSON (сохранить файл).
3. Импорт:

```bash
cd backend
.venv/bin/python scripts/import_cookies.py --file ~/Downloads/cookies.json
# или строкой из DevTools:
.venv/bin/python scripts/import_cookies.py --cookie "v=...; u=...; ft=..."
```

Скрипт добавит cookies в профиль, откроет страницу поиска и проверит доступ:
`OK: доступ есть` или `FAIL: cookies не дали доступ` (обновите cookies).

## Проверка, что всё работает

```bash
cd backend
.venv/bin/python scripts/fetch_page.py --browser \
  --url "https://www.avito.ru/moskva/telefony?q=iphone+15" --out /tmp/page.html
```

Ожидаемо: `page 1: 50 listings` и карточки с ценами. Если ноль — обновите профиль
(способ 1 или 2).

## Сервер (без рабочего стола)

- В Docker браузерный воркер уже запускается под **Xvfb** (`xvfb-run`, `BROWSER_HEADLESS=false`),
  профиль живёт в томе `browserdata`.
- Локально воркер запускается из Chrome-кэша хоста: `make up-dev` (без скачивания
  Chromium в образ). На сервере соберите self-contained образ: `INSTALL_BROWSER=1 docker compose build worker`.
- Первичное доверие на сервере получают так: импортируют cookies (`import_cookies.py`
  можно запускать в контейнере — окно уходит на Xvfb и не мешает) **или** копируют
  готовый профиль с ноутбука в том:

```bash
docker compose cp backend/.browser-profile/. worker:/data/browser-profile
```
- Для объёмов и стабильности используйте **пул прокси**:
  ```bash
  # .env
  PROXY_ENABLED=true             # без этого движок ходит напрямую (с вашим IP)
  PROXY_LIST=http://user:pass@host1:8000,socks5://host2:1080,host3:8000:user:pass
  PROXY_ROTATION=round_robin     # или random
  PROXY_MAX_FAILURES=3           # после скольких ошибок прокси в кулдаун
  PROXY_COOLDOWN_SECONDS=300
  PROXY_ANTIBOT_COOLDOWN_SECONDS=1800  # метка «Авито блокирует» (не кулдаун)
  PROXY_HEALTHCHECK_ENABLED=true # проверка выхода и IP
  ```
  Форматы записей: `http://user:pass@host:port`, `socks5://host:port`,
  `host:port:user:pass`, `host:port` (без схемы — http). Ротационные прокси
  (один endpoint, меняющий IP на каждый запрос) указываются одной записью.
- **Что брать:** для браузерного транспорта — **HTTP/HTTPS** (Chromium не умеет
  авторизацию в SOCKS5); для HTTP-транспорта (curl_cffi) подойдут и HTTP, и SOCKS5.
  Резидентные/мобильные IP дают меньше челленджей, чем датацентр.
- **Важно:** «прокси живой» ≠ «Авито его пускает». Датацентр-диапазоны фаервол режет
  (`403` + «доступ ограничен») даже с валидной авторизацией. Пул различает причины:
  `failures`/кулдаун — сетевые сбои, `antibot_blocked` — сайт не пускает этот выход.
  Панель показывает «Авито блокирует · N мин», а челлендж не отправляет рабочий прокси
  в кулдаун.
- Пул сам выбирает живой прокси (не в кулдауне и не под antibot-меткой), по кругу или
  рандомом; упавшие временно исключаются и возвращаются после healthcheck. Статусы и
  внешний IP видны на главной панели в блоке «Прокси», там же кнопка «Проверить»
  (`GET /api/v1/proxies`, `POST /api/v1/proxies/check?avito=true` — с проверкой Авито).
- Один прокси ↔ один профиль: не смешивайте выходные IP у одного профиля продавца.

## Диагностика

| Симптом | Причина | Действие |
|---|---|---|
| Пустая страница, 0 карточек, title «Авито» | headless-детект | `BROWSER_HEADLESS=false` (+ Xvfb на сервере) |
| «Доступ ограничен: проблема с IP» / 439 / hCaptcha | фаервол не доверяет сессии | `make cookies` (свежие cookies из браузера) или `make browser-login` |
| `403` на всех прокси, а прямой канал работает | датацентр-диапазон режется фаерволом | панель покажет «Авито блокирует»; взять резидентные/мобильные прокси либо `PROXY_ENABLED=false` |
| 429 на поиске даже со свежими cookies | IP/сессия перегреты прошлыми обходами | `make cookies --fresh`, выждать кулдаун (CrawlGuard), уменьшить частоту |
| Браузер не стартует, `DISPLAY` пуст | stale-lock Xvfb после рестарта | перезапустить воркер (в CMD уже чистим `/tmp/.X99-lock`) |
| Внезапно снова капча | истёк/недостаточен профиль, сменился IP | повторить `make cookies`; закрепить прокси за профилем |

## Безопасность и правила

- Cookies и профиль — это доступ к аккаунту: храните локально, не публикуйте.
- Для автоматизации лучше отдельный аккаунт, отдельный профиль и отдельный прокси.
- Соблюдайте умеренную частоту: паузы 8–20 секунд, до 10 страниц за обход,
  расписание 1–2 часа и реже на старте. Парсинг публичных страниц — на ваш риск и
  в рамках действующих правил площадки.
- Телефоны и персональные данные проект не собирает.
